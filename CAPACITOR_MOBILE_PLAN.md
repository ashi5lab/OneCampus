## Phase 2: Capacitor Config

`client/capacitor.config.json` (generated by `cap init`, needs edits):

```json
{
  "appId": "online.onecampusedu.app",
  "appName": "OneCampus",
  "webDir": "dist",
  "server": {
    "androidScheme": "https"
  }
}
```

- `webDir: "dist"` — Capacitor bundles your Vite build output (`npm run build`) into the native app. Every `cap sync` re-copies the latest `dist/` into both native projects.
- **Important architectural question to resolve here:** does the app ship as a **fully offline-bundled** web app (dist/ baked into the binary, calls your API remotely), or does it **live-load** from a hosted URL (like a thin native wrapper around your Railway-deployed site)? Recommendation: **bundle `dist/` into the binary** (standard Capacitor pattern) — API calls still go to your real backend over HTTPS, only the UI shell ships in the binary. This means app updates for UI changes require a new app store release OR you adopt Capacitor's live-update mechanism later (out of scope for now).

**Checklist:**
- [ ] Edit `capacitor.config.json` with final `appId`/`appName`
- [ ] Confirm `client/.env` production API URL is correct for what the bundled app will call (this is now a fixed URL baked into the build, not `localhost`)
- [ ] Run `npm run build` once locally to confirm `dist/` still generates cleanly

## Phase 3: Native Push Notifications (swap Web FCM → Native FCM)

Currently `client/src/lib/firebase.js` uses the **Firebase Web SDK** (`firebase/messaging`, service worker–based). Inside a Capacitor app, push should instead use the **native FCM SDK** via a Capacitor plugin — same Firebase project, same backend, different token registration path.

```bash
npm install @capacitor/push-notifications
```

**What changes:**
- New: `client/src/lib/nativePush.js` — wraps `@capacitor/push-notifications`'s `PushNotifications.register()`, `addListener('registration', ...)`, `addListener('pushNotificationReceived', ...)`.
- Detection: app needs to know "am I running inside Capacitor or in a regular browser?" — use `Capacitor.isNativePlatform()` from `@capacitor/core` to branch between the existing web FCM path (`lib/firebase.js`) and the new native path.
- **Backend requires ZERO changes** — `onec_fcm_tokens` table already stores tokens generically; `sendPush.js`'s `admin.messaging().sendEachForMulticast()` already routes to the correct channel (Web Push vs APNs/FCM native) automatically based on token type. This was already anticipated in `NOTIFICATION_SYSTEM_COMPLETE.md`'s "Future: Mobile (Native)" section.
- Android: needs `google-services.json` (from Firebase Console → Project Settings → Android app) placed in `client/android/app/`.
- iOS: needs `GoogleService-Info.plist` (from Firebase Console → Project Settings → iOS app) placed in `client/ios/App/App/`, **plus** an APNs Auth Key uploaded to Firebase Console (Project Settings → Cloud Messaging → Apple app configuration) — this requires the Apple Developer account from Decision 1.

**Checklist:**
- [ ] Register Android app in Firebase Console → download `google-services.json`
- [ ] Register iOS app in Firebase Console → download `GoogleService-Info.plist`
- [ ] Install `@capacitor/push-notifications`
- [ ] Write platform-detection branch (native vs web push)
- [ ] iOS APNs key upload (blocked on Decision 1)

## Phase 4: GitHub Actions — Android Build

New file: `.github/workflows/android-build.yml`

```yaml
name: Android Build
on:
  workflow_dispatch:
  push:
    branches: [main]
    paths: ['client/**']

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17
      - name: Install deps & build web assets
        working-directory: client
        run: |
          npm ci
          npm run build
      - name: Sync Capacitor
        working-directory: client
        run: npx cap sync android
      - name: Build debug APK
        working-directory: client/android
        run: ./gradlew assembleDebug
      - uses: actions/upload-artifact@v4
        with:
          name: onecampus-debug-apk
          path: client/android/app/build/outputs/apk/debug/app-debug.apk
```

- This produces a **debug APK** as a downloadable workflow artifact — no signing needed, matches Decision 2 Option A.
- If Decision 2 comes back as Option B (Play Store), this workflow gets a second job for `assembleRelease` with a signing keystore stored as a GitHub secret (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, etc.) plus a `fastlane` or direct Play Console API upload step.

**Checklist:**
- [ ] Create `.github/workflows/android-build.yml`
- [ ] Push and confirm the workflow runs successfully in the Actions tab
- [ ] Download the artifact APK, sideload onto a test Android phone, confirm it launches and logs in

name: iOS Build Check
on:
  workflow_dispatch:
  push:
    branches: [main]

  build:
    runs-on: macos-latest

      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

          xcodebuild -workspace App.xcworkspace -scheme App \

## Known Capacitor-Specific Gotchas to Watch For

- **Android hardware back button** — needs explicit handling (`App.addListener('backButton', ...)` from `@capacitor/app`) or it can exit the app unexpectedly from nested screens.
- **Safe area insets** — iOS notch/Dynamic Island and Android gesture nav bars need CSS `env(safe-area-inset-*)` — check if your existing responsive CSS already accounts for this (likely partially, from the PWA work).
- **Status bar styling** — `@capacitor/status-bar` plugin needed to control status bar color/text (light/dark) to match your theme.
- **Splash screen** — `@capacitor/splash-screen` plugin; you already have `apple-splash-*.png` assets from the PWA setup, may be reusable.
- **Deep linking** — if any push notification `url` deep-links into the app, Capacitor needs App Links (Android) / Universal Links (iOS) configuration — not yet scoped, revisit once basic push works.
- **Keyboard behavior** — WebView keyboard can behave differently than desktop browser; test all forms (login, messages, attendance search).
